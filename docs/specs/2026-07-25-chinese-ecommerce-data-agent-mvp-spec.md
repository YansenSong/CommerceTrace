## Problem Statement

项目需要在约 8 周、100 小时的第一版预算内，形成一个适合简历展示、能够真实运行和复现评测的中文电商经营分析 Data Agent。它不能只是把自然语言一次性翻译成 SQL，也不能为了追求“平台化”而复制成熟开源项目的全部复杂度。

用户需要用中文提出“销售额为什么下降”之类的问题，让系统在一个小型 PostgreSQL 电商数据集上完成有限的多步分析，通过只读 SQL 的真实执行结果给出可追踪结论。系统还需要积累真正被最终答案采用的成功工具经验，但必须防止“SQL 能执行”被误认为“SQL 语义正确”，从而污染长期记忆。

现有成熟方案中的多数据库、多模型、多 Agent、通用插件、生产级分布式部署和复杂权限并不是本项目的目标。第一版需要把精力集中在单 Agent Tool-calling、执行反馈与自我修正、证据账本、Candidate/Trusted Memory 边界、SQL 双层只读安全以及可复现评测上。

## Solution

构建一个独立实现的、面向中文电商经营分析的轻量 Data Agent。系统采用 React 前端、FastAPI API、单 Agent Tool-calling 循环、PostgreSQL 与嵌入式 ChromaDB，并通过 Docker Compose 从空环境启动。

每个请求在第一次模型调用前确定性地装配完整压缩 Schema、相关业务规则、Trusted SQL 和至多两条 Candidate 经验。Agent 显式经历理解、必要澄清、检索、计划、执行、观察、自我修正、综合和记忆登记阶段，通过 `run_sql`、`visualize_data` 与 `search_memory` 完成分析。

所有定量结论必须引用由已执行查询生成的 Evidence。PostgreSQL 只读角色与应用层 SQL AST 校验共同阻止写入、越权和危险查询。最终答案引用的成功 SQL 由后端自动登记为 Candidate；只有通过 Golden Case 离线回放的 Candidate 才能晋升为 Trusted。

系统通过 POST 建立请求并使用 SSE 输出结构化计划、工具状态、Evidence、图表和答案增量。正式评测固定数据种子、模型参数、Prompt 版本和知识版本，报告执行正确率、安全性、证据完整性、调用成本以及持续记忆对 Cold/Warm Run 的影响。

## User Stories

1. 作为中文电商经营人员，我希望用中文提出经营问题，以便不编写 SQL 也能分析业务数据。
2. 作为中文电商经营人员，我希望系统先给结论再给证据，以便快速理解分析结果。
3. 作为中文电商经营人员，我希望询问销售额下降原因，以便定位主要相关因素。
4. 作为中文电商经营人员，我希望系统把复杂归因问题拆成有限步骤，以便理解分析路径。
5. 作为中文电商经营人员，我希望看到当前分析步骤和完成进度，以便知道系统正在做什么。
6. 作为中文电商经营人员，我希望看到工具运行状态，以便区分检索、查询、修正和可视化阶段。
7. 作为中文电商经营人员，我希望每个定量结论都能展开对应证据，以便核对数字来源。
8. 作为中文电商经营人员，我希望查看证据所用 SQL、结果表格、执行时间和结果哈希，以便复核分析。
9. 作为中文电商经营人员，我希望系统区分描述性贡献与严格因果，以便避免夸大分析结论。
10. 作为中文电商经营人员，我希望系统在销售额、退款或比较基准存在实质歧义时澄清，以便得到符合口径的结果。
11. 作为中文电商经营人员，我希望系统只在歧义会改变结果时追问，以便避免不必要的交互。
12. 作为中文电商经营人员，我希望系统在达到分析预算时返回已有证据、未完成步骤和停止原因，以便获得可用的部分结果。
13. 作为中文电商经营人员，我希望系统能展示指标卡、柱状图、折线图和饼图，以便快速识别趋势和贡献。
14. 作为中文电商经营人员，我希望图表字段来自真实查询结果，以便避免模型编造可视化数据。
15. 作为中文电商经营人员，我希望保存并浏览自己的历史对话，以便继续或回放过去的分析。
16. 作为匿名用户，我希望无需注册即可开始使用，以便降低演示门槛。
17. 作为匿名用户，我希望自己的对话与其他匿名用户隔离，以便避免数据串读。
18. 作为匿名用户，我希望刷新页面后仍能通过安全 Cookie 找回对话，以便保持连续体验。
19. 作为用户，我希望系统不显示模型隐藏思维，以便只接收可验证的结构化过程。
20. 作为用户，我希望完整 Prompt、密钥、连接信息和原始技术错误不会泄露，以便保护系统安全。
21. 作为用户，我希望空查询结果被当作可分析结果而不是系统故障，以便系统能够检查筛选条件或确认确实无数据。
22. 作为用户，我希望系统在不确定低基数业务值时安全探索允许的候选值，以便减少因枚举值猜测造成的错误。
23. 作为用户，我希望客户姓名、地址和联系方式等敏感字段不能被值级探索，以便保护隐私。
24. 作为 Data Agent，我希望每次请求都获得完整压缩 Schema，以便在约八张表的小型数据库中稳定选择表和字段。
25. 作为 Data Agent，我希望 Schema 包含中文含义、英文标识符、关系、必要枚举、版本和指纹，以便准确理解数据库结构。
26. 作为 Data Agent，我希望首次模型调用前自动获得核心上下文，以便不依赖模型主动记得调用检索工具。
27. 作为 Data Agent，我希望在多步分析中按原问题和当前步骤继续检索记忆，以便补充特定步骤的经验。
28. 作为 Data Agent，我希望只通过原生 Tool Calling 使用受控工具，以便让参数、结果和轨迹都可验证。
29. 作为 Data Agent，我希望 SQL 错误以脱敏、结构化且带可重试标记的形式返回，以便安全地自我修正。
30. 作为 Data Agent，我希望同一分析目的最多修正两次 SQL，以便限制无效循环和成本。
31. 作为 Data Agent，我希望每个请求最多进行十轮工具调用和五次业务 SQL，以便保证延迟与费用可控。
32. 作为 Data Agent，我希望不猜测数据库值或查询结果，以便所有结论都有事实依据。
33. 作为 Data Agent，我希望为每次 `run_sql` 声明查询目的和预期列，以便把工具调用关联到计划、Evidence 和记忆。
34. 作为 Data Agent，我希望只能执行单条只读 PostgreSQL 查询，以便不能修改业务数据。
35. 作为 Data Agent，我希望无法访问应用内部 Schema，以便对话、身份和记忆记录不会被业务查询读取。
36. 作为 Data Agent，我希望普通查询结果受行数限制，以便防止大结果耗尽上下文和服务资源。
37. 作为 Data Agent，我希望可视化工具只生成受控 Plotly JSON，以便不需要执行任意 Python。
38. 作为系统维护者，我希望 PostgreSQL 和版本库知识文件是权威事实源，以便业务事实可审查和版本化。
39. 作为系统维护者，我希望 ChromaDB 只是可重建派生索引，以便索引损坏或删除后能够恢复。
40. 作为系统维护者，我希望业务知识与工具经验使用独立索引，以便分别检索和管理。
41. 作为系统维护者，我希望只使用一个中文 Embedding 模型，以便缩小依赖和评测变量。
42. 作为系统维护者，我希望 Candidate 每次最多召回两条且排名低于 Trusted，以便限制未经验证经验的影响。
43. 作为系统维护者，我希望 Candidate 在 Prompt 中明确标记为未经验证，以便 Agent 不把历史经验当成事实。
44. 作为系统维护者，我希望历史 SQL 每次都重新校验和执行，以便不复用可能过时的查询结果。
45. 作为系统维护者，我希望只把被最终 Evidence 引用的成功 SQL 登记为 Candidate，以便过滤临时探索和无用查询。
46. 作为系统维护者，我希望 Candidate 保存问题、分析步骤、规范化 SQL、涉及字段、版本、执行摘要和结果哈希，以便后续检索、验证和去重。
47. 作为系统维护者，我希望不保存完整结果、模型思维、失败轨迹和临时探索文本，以便控制隐私、存储和错误传播风险。
48. 作为系统维护者，我希望 Candidate 只有通过 Golden Case 回放才能晋升 Trusted，以便语义正确性有可复现依据。
49. 作为系统维护者，我希望 Schema 指纹或指标版本变化时相关记忆变为 Stale，以便旧经验不会静默污染新查询。
50. 作为系统维护者，我希望安全失败或 Golden 回放失败的经验变为 Rejected，以便阻止再次召回。
51. 作为系统维护者，我希望无需打扰真实用户确认每个答案，以便自动积累候选经验而不破坏体验。
52. 作为系统维护者，我希望通过冷启动命令载入业务规则、指标和 Golden SQL 并重建索引，以便从空环境稳定初始化。
53. 作为系统维护者，我希望只读角色、只读事务和语句超时在数据库层再次约束查询，以便应用层校验失误时仍有保护。
54. 作为系统维护者，我希望数据库错误在返回模型前脱敏，以便不泄露内部结构和凭据。
55. 作为系统维护者，我希望所有 SSE 事件拥有事件、会话、请求、时间和结构化载荷标识，以便前端可靠渲染和排障。
56. 作为前端开发者，我希望按事件标识去重 SSE 事件，以便避免界面重复展示状态和证据。
57. 作为评测负责人，我希望使用固定种子生成带可控业务异常的中文电商数据，以便稳定验证归因能力。
58. 作为评测负责人，我希望订单、明细、支付、退款和库存满足业务一致性约束，以便 Golden 结果可信。
59. 作为评测负责人，我希望同一配置与种子产生相同结果哈希，以便复现实验。
60. 作为评测负责人，我希望评测集覆盖简单聚合、多表指标、多步归因、歧义、无法回答和危险请求，以便全面检验 MVP。
61. 作为评测负责人，我希望用 Golden SQL、结果哈希和场景断言作为主要真实标签，以便不依赖 LLM Judge 的主观判断。
62. 作为评测负责人，我希望分别测量执行正确率、归因命中、SQL 修正、澄清、安全、证据完整性、召回、成本和污染率，以便识别系统短板。
63. 作为评测负责人，我希望 Cold Run 清空 Candidate 后执行第一组问题，以便测量没有运行时经验时的基线。
64. 作为评测负责人，我希望 Warm Run 使用语义相近但措辞不同的问题，以便证明记忆复用而不是相同问题缓存。

## Implementation Decisions

- 第一版是独立实现的中文电商经营分析 Data Agent，借鉴 Vanna 2.0 的单 Agent Tool-calling、工具记忆与流式组件理念，但不 Fork、裁剪或复刻其完整工程。
- 技术栈固定为 React 与 TypeScript 前端、FastAPI 后端、PostgreSQL、嵌入式 ChromaDB、原生 Tool Calling 的单一 OpenAI-compatible LLM 客户端、`BAAI/bge-small-zh-v1.5` Embedding 和 Docker Compose。
- 系统采用单 Agent，不使用 LangChain、LangGraph 或多 Agent。API 层只负责身份、会话、请求、SSE 与依赖装配，不承载 Agent 决策。
- Agent Core 维护显式请求状态，包括会话与请求标识、用户问题、分析计划、当前步骤、检索上下文、工具轮数、业务 SQL 次数、重试次数、Evidence、生成组件和终态。
- Agent 状态流为 Understand、必要时 Clarify、Retrieve、Plan、Act、Observe、Synthesize、Remember。简单问题生成一个计划步骤，归因问题最多五个可展示步骤。
- 每个请求最多十轮工具调用、五次业务 SQL；同一目的的 SQL 最多修正两次。预算耗尽后返回已有证据、未完成步骤和停止原因。
- Tool Registry 只提供 `run_sql`、`visualize_data` 和 `search_memory`。所有工具参数使用 Pydantic 契约校验。
- Candidate 保存不是 LLM 工具。后端在最终 Evidence 确定后登记符合门槛的成功 SQL，避免让 Agent 自己决定何为可信记忆。
- 第一次模型调用前，Context Assembler 确定性注入完整压缩 Schema、相关业务规则和指标、Trusted SQL 以及至多两条 Candidate。后续步骤可按“原始问题＋当前步骤”主动调用 `search_memory`。
- 业务数据库规模约八张表，因此固定注入完整 Schema，不实现 Schema Selector，也不把 Schema 放入向量索引。Schema 从 PostgreSQL 元数据生成，包含中文含义、英文标识符、主外键、必要枚举、版本与指纹。
- PostgreSQL 分为 `ecommerce` 业务 Schema 和 `agent_app` 应用 Schema。`run_sql` 使用的角色只能读取 `ecommerce`，不能读取 `agent_app`。
- 业务模型包含客户、品类、商品、订单、订单明细、支付、退款和每日库存快照，支持订单量、客单价、地区、品类、渠道、取消、退款与库存等预定义经营分析维度。
- SQL 工具请求包含 SQL、分析目的和预期列。成功结果包含列、行数、预览、执行时间和结果哈希；失败结果包含安全错误码、脱敏错误信息和是否可重试。
- 应用层通过 PostgreSQL 方言 AST 解析，只允许单条 `SELECT`、`WITH ... SELECT` 与受控 `EXPLAIN`，禁止 DDL、DML、多语句、危险函数、非允许 Schema 和越权对象。
- 数据库层使用独立只读角色、只读事务、连接池和 `statement_timeout`。连接字符串、数据库用户和密码永不进入模型上下文。
- 普通查询最多返回 500 行。低基数值探索复用通用只读 SQL，仅允许白名单中的非敏感列且最多返回 50 个候选值。
- 第一版不实现专用 `search_column_values`、`resolve_entity` 或实体向量索引；候选值仍有实质歧义时向用户澄清。
- Evidence 关联分析步骤、工具调用、主张、SQL、列、行数、结果哈希和执行时间。每个最终定量主张必须引用至少一个 Evidence 标识。
- 多步归因只做有限描述性归因：确认总体变化，拆分订单量和客单价，按地区与品类分析贡献，检查取消、退款和库存影响，最后汇总主要相关因素。
- 最终措辞使用“主要相关因素”“贡献”或“数据表明”，不宣称严格因果。
- `visualize_data` 只接受结构化图表参数并返回受控 Plotly JSON，支持指标卡、柱状图、折线图和饼图；后端验证图表字段存在于对应查询结果。
- Schema 的权威来源是 PostgreSQL。业务规则、指标定义与 Golden SQL 的权威来源是版本化知识文件。运行时记忆登记的权威来源是 PostgreSQL。
- ChromaDB 仅是派生召回索引，分为业务记忆与工具记忆两个集合，可从权威事实源完全重建。
- 长期工具记忆状态为 Candidate、Trusted、Stale 和 Rejected。Candidate 是被最终答案采用但未经标准答案验证的经验；Trusted 是预置 Golden SQL 或通过 Golden Case 回放的 Candidate。
- 任意真实问题的经验不会因多次执行成功自动晋升 Trusted。Candidate 召回数最多为二、排序权重低于 Trusted、上下文中明确标记为未验证，并在使用前检查 Schema 指纹与指标版本。
- 历史 SQL 每次都重新进行安全校验和真实执行，不复用历史结果。
- 记忆记录保留问题、分析步骤、规范化 SQL、涉及表列、Schema 指纹、指标版本、执行时间、行数、列名、有限摘要、结果哈希、状态、创建时间和最后验证时间。
- 不保存完整查询结果，不向量化模型隐藏思维、失败轨迹或临时探索文本。
- Schema、字段或指标版本变化时相关记忆转为 Stale；安全验证或 Golden 回放失败时转为 Rejected。
- 冷启动流程读取版本化业务知识和 Golden SQL，写入 PostgreSQL 记忆登记并构建 ChromaDB 索引；索引可以独立删除并重建。
- 合成数据使用固定随机种子和 YAML 场景配置，采用中文展示数据和受控统计分布，批量导入 PostgreSQL；仓库只保存生成逻辑、配置、种子和场景，不保存完整生成数据。
- 数据中植入四类上游场景：华东订单量下降、数码退款率上升、信息流新客增长但复购低、库存不足导致取消增加。不得事后硬改聚合结果。
- 应用采用匿名安全 Cookie 身份，不实现注册登录。PostgreSQL 精确保存匿名用户、对话、消息、工具调用、工具结果、Evidence 和记忆记录；所有对话查询按匿名用户隔离。
- 前端通过 `fetch()` POST 并解析 SSE，展示对话历史、计划、步骤状态、工具状态、证据卡片、结果表格、Plotly 图表和最终中文结论。
- SSE 事件覆盖会话开始、上下文检索、计划创建、步骤开始、工具开始/完成/失败、Evidence 创建、图表创建、答案增量/完成和请求失败。
- 所有 SSE 事件包含事件标识、会话标识、请求标识、时间戳和结构化载荷；前端按事件标识去重。第一版不实现跨进程断点续传。
- 模型隐藏思维、完整 Prompt、密钥、连接信息和原始技术错误永不展示；完整 SQL 和工具参数默认折叠但可由用户展开核验。
- 评测集约 60 个中文问题，覆盖单表与聚合、多表与业务指标、多步归因、歧义与无法回答、危险 SQL 与越权请求。
- 预置 Trusted Memory 与最终评测集隔离，评测问题及其表达方式不能提前写入记忆。
- 主要真实标签来自 Golden SQL、结果哈希和场景断言，不以 LLM Judge 作为主要标签。
- 持续记忆实验使用清空 Candidate 的 Cold Run 和措辞不同但语义相近的 Warm Run；不以重复完全相同的问题证明记忆有效。
- 消融实验依次比较完整 Schema 与 System Prompt、业务规则与 Trusted SQL、执行反馈与自我修正、Candidate 持续记忆。
- 第一版验收目标为总体执行结果正确率不低于 80%、多步归因正确率不低于 70%、危险 SQL 拦截率 100%、定量结论 Evidence 引用完整率 100%，且 Candidate 不导致 Warm Run 正确率下降。
- 上述指标只有在固定种子、模型参数、Prompt 版本与知识版本下实际运行评测后才能作为项目成果。
- 交付按八周控制范围：工程与数据、Agent 与 SSE、上下文与记忆、安全与证据、多步归因、前端、评测实验、测试与文档。

## Testing Decisions

- 主测试接缝只有一个：从 FastAPI 的中文提问请求进入，消费完整 SSE 事件流，并断言最终外部行为，包括计划、工具状态、Evidence、答案引用、图表契约、预算终止信息以及 PostgreSQL 中允许观察的对话和 Candidate 副作用。
- 主接缝使用确定性 Fake LLM、固定种子 PostgreSQL 数据和可重建 ChromaDB 索引。这样可以在不依赖真实模型随机性与费用的情况下覆盖完整单 Agent 工具循环。
- 好测试只断言外部行为和稳定契约，不断言 Prompt 的逐字内容、私有方法调用顺序、内部类结构或模型隐藏思维。
- 主接缝覆盖简单聚合、多表指标、多步归因、必要澄清、空结果、SQL 可修正错误、预算耗尽、危险 SQL、越权访问、图表生成、Candidate 登记和 SSE 去重所需标识。
- SQL 安全使用窄合同测试补充主接缝，覆盖允许的单条只读查询、CTE、受控 EXPLAIN，以及 DDL、DML、多语句、危险函数、非允许 Schema、敏感值探索和行数限制。
- Agent 状态与预算使用纯状态机合同测试，断言允许的终态、工具轮数、业务 SQL 次数、每目的重试次数和部分结果返回，不绑定具体实现类。
- Context Assembler 测试断言首轮必含完整 Schema、业务规则、Trusted SQL、最多两条低权重 Candidate、版本和指纹；不进行 Prompt 字符串快照。
- Evidence 测试断言每个定量主张都引用真实已执行查询，且引用可追溯到步骤、工具调用和结果哈希。
- Memory 测试断言 Candidate 的登记门槛、规范化去重、召回上限、Trusted 优先级、Golden 回放晋升、失败拒绝及版本变化失效。
- 存储集成测试断言 PostgreSQL 只读角色不能写入或访问 `agent_app`，对话按匿名用户隔离，ChromaDB 删除后可从权威事实源重建。
- 可视化合同测试断言图表类型受控，所用字段存在于真实查询结果，且不会执行任意 Python。
- 数据生成测试断言主外键、订单与支付退款一致性、金额可重算、植入异常达到最小效果、Golden 结果稳定及相同种子产生相同哈希。
- 正式真实模型评测与普通快速测试分开标记；真实模型评测固定模型参数、Prompt 版本、知识版本、数据种子并输出 Markdown 与 JSON 报告。
- 仓库当前没有实现代码或既有测试可作为直接 prior art；本规格沿用已确认设计中的“确定性 Fake LLM 完整工具循环、PostgreSQL/ChromaDB 集成测试和固定版本正式评测”作为首批测试范式。

## Out of Scope

- PostgreSQL 之外的业务数据库。
- 多 LLM 厂商适配器或不支持原生 Tool Calling 的模型。
- LangChain、LangGraph、多 Agent、Planner/Reviewer 拆分或通用 Agent 编排平台。
- Schema Selector、大规模企业数据仓库 Schema 路由、独立 Schema 向量索引。
- 注册、登录、OAuth、复杂权限、行级权限、多租户、配额和计费。
- 任意 Python、Shell、文件执行或用户自定义代码运行。
- 预测模型、推荐系统、严格因果推断和通用数据科学平台。
- 商品级自由文本实体解析、专用实体工具和独立实体向量索引。
- 语音、文件上传、联网搜索和移动端 App。
- Kubernetes、Redis、消息队列、微服务、生产级高并发和高可用。
- 通用 Prompt 管理平台、多向量库适配器和生产级可观测平台。
- 跨进程 SSE 断点续传。
- 第一版人工记忆审核或标注页面。
- 保存完整查询结果、模型隐藏思维、失败轨迹和临时探索文本作为长期记忆。
- 把真实用户问题的重复执行成功直接当作 Trusted 晋升依据。
- 复刻 Vanna 的框架无关 Web Component、Storybook 工程或全部平台能力。

## Further Notes

- 本规格记录的是 2026-07-25 会话中已经确认的架构与范围，不替代更细的实现计划。
- 设计的两条产品主线是“有限多步经营归因”和“Candidate/Trusted 持续工具记忆”；其余能力应服务于可靠性、可追踪性、安全性与可复现评测。
- 第一版时间盒为 8 周、约 100 小时。达到上限后停止扩展，优先保证 Docker Compose 演示、测试、评测报告、README 和架构说明完整。
- 完成标准包括：从空环境启动；中文简单查询与有限归因可用；对话、工具轨迹和 Evidence 可回放；Candidate 与 Trusted 边界可验证；索引可重建；危险 SQL 被双层阻止；评测和消融可复现。
- 当前仓库没有配置远端或 issue tracker，因此本文件是可直接发布的 issue 正文来源；发布时只应用 `ready-for-agent` 标签，无需附加其他 triage 标签。
